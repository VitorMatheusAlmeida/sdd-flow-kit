# sdd-flow-kit

A drop-in **spec-driven development** setup for [Claude Code](https://claude.com/claude-code). Copy it into a project, fill in one file (`sdd.config.json`), and you get:

- **[GitHub Spec Kit](https://github.com/github/spec-kit)**, already installed (Claude integration): `/speckit-specify → /speckit-plan → /speckit-tasks → /speckit-implement`.
- **Flowcharts and walkthrough scripts** per feature (`speckit-flows`): a detailed `fluxos.drawio` you can edit in draw.io (the whole process map on the first page, then one page per journey), and one test script per user journey. Your edits to the drawing are read, judged and turned into impact on scripts, spec and tasks.
- **Table diagrams** per feature (`speckit-tables`): one `tabelas.planejado.dbml` to paste into [dbdiagram.io](https://dbdiagram.io), with only the tables of the spec as they will be (new and changed), the tables they reference and the enums they use, so it opens on its own. A checker lists what changes against the current schema; your edits made in dbdiagram are judged before they are kept.
- **Flow walkthroughs** (`flow-walkthrough`): a manual test battery with fixes for each journey — 18 points per screen and route, a matrix generated from the code, scans of code, API, security, accounts and screens, captures at every viewport, and a second round before the PR.
- **Code-quality skills**: `clean-code`, `modulos-backend` (NestJS + Prisma module structure, queries, cache and queues) and `code-analyze` (reviews that hunt bugs and flow problems).
- **Project hygiene**: husky hooks that lint and run **only the tests related to the staged files**, Conventional Commits, ESLint architecture rules, issue and PR templates.

Everything project-specific lives in `sdd.config.json`. No skill hard-codes a path, an account or a rule of your project.

## How it fits together

`/speckit-flows` and `/speckit-tables` are optional but recommended, like `/speckit-clarify`: the spec-kit hooks suggest them at the right point of the cycle, and they run only when you invoke them. Skip one only when the feature has nothing for it (no journeys, no tables).

```text
/speckit-specify ─► spec.md (flows, preserved behaviour for refactors)
/speckit-plan ────► plan.md, data-model, contracts
                    └─ recommended ─► /speckit-tables ─► tabelas.planejado.dbml (dbdiagram)
                                    └ /speckit-flows ──► fluxos.drawio + roteiros/R##-*.md
/speckit-tasks ───► tasks.md
                    └─ recommended ─► /speckit-flows ──► one "walkthrough of R##" task per script
/speckit-implement► code
                    └─ recommended ─► /speckit-tables ─► planned file checked against the real schema
/speckit-converge ◄─ recommended ──── absorb your edits to fluxos.drawio and tabelas.planejado.dbml (judged, not blindly applied)
walkthrough R## ──► flow-walkthrough: matrix-R##.md, scans, captures, fixes, second round ─► PR on request
```

## Requirements

| Tool | Why | Required |
|---|---|---|
| [Claude Code](https://claude.com/claude-code) | runs the skills and the spec-kit commands | yes |
| Node.js **22+** | the kit scripts (no npm dependencies; built-in `fetch` and `WebSocket`) | yes |
| git | history is the base for "what changed" in drawings and diagrams | yes |
| PowerShell (Windows PowerShell 5.1, or [PowerShell 7](https://learn.microsoft.com/powershell/scripting/install/installing-powershell) `pwsh` on macOS/Linux) | the bundled spec-kit scripts are the PowerShell variant | yes |
| Chrome or Edge | screen scans and captures (headless, no extension). Other path: set `SDD_BROWSER` | for walkthroughs |
| [draw.io](https://www.drawio.com) (desktop, VS Code extension or app.diagrams.net) | to view and edit `fluxos.drawio` | to edit flows |
| Prisma + [`prisma-dbml-generator`](https://www.npmjs.com/package/prisma-dbml-generator) | produces `dbml/schema.dbml`, the source of the table diagrams | for tables |
| [Specify CLI](https://github.com/github/spec-kit) | only to upgrade spec-kit or switch to the bash variant | optional |

The code-quality skills assume a **NestJS + Prisma** backend and a React/Next frontend; the walkthrough discovers screens and routes for `next-app-router` and `nestjs`, and works with any stack in `manual` mode.

## Install

```bash
git clone https://github.com/VitorMatheusAlmeida/sdd-flow-kit.git
node sdd-flow-kit/install.mjs path/to/your-project --dry-run   # see what would be copied
node sdd-flow-kit/install.mjs path/to/your-project
```

The installer copies `template/` into the project and **never overwrites** an existing file: it lists the ones it kept so you can merge them by hand (`--force` overwrites, `--only <prefix,...>` limits the copy). Copying `template/` by hand works too — remember the dotfolders (`.claude`, `.specify`, `.husky`, `.github`).

**Already using spec-kit?** Copy only the kit's additions and keep your installation:

```bash
node sdd-flow-kit/install.mjs your-project --only .claude/skills/speckit-flows,.claude/skills/speckit-tables,.claude/skills/flow-walkthrough,.claude/skills/clean-code,.claude/skills/modulos-backend,.claude/skills/code-analyze,.specify/scripts/node,.specify/templates/overrides,.specify/templates/roteiro-template.md,.specify/sdd.config.schema.json,sdd.config.json
```

Then add the hooks of `template/.specify/extensions.yml` to your `.specify/extensions.yml`.

**Skills for every project** (optional): `node install.mjs --user` copies `clean-code`, `modulos-backend`, `code-analyze` and `flow-walkthrough` to `~/.claude/skills`. Remove the project copies afterwards to avoid two versions. The `speckit-*` skills always stay per project, because they depend on `.specify/`.

## Configure

### 1. `sdd.config.json`

At the project root; your editor validates and completes it through `.specify/sdd.config.schema.json`. Relative paths are relative to the file.

| Section | What to fill in |
|---|---|
| `project` | `name`; `locale` — the language of every generated document (`pt-BR` and `en` are built in) |
| `git` | `baseBranch` — where features start and merge |
| `frontend` | `root` (source), `pages` (router folder), `router`: `next-app-router` \| `manual` \| `none`. A frontend in another repository: a relative path to its checkout |
| `backend` | `root`, `framework`: `nestjs` \| `manual` \| `none`, `healthPath`, `docsPath` (Swagger), `errorShape` (fields of an error body) |
| `auth` | how scripts sign in with test accounts: `loginPath`, `loginBody` (`{email}`, `{password}`), `tokenPath`, `headerScheme`, `cookieName` (the cookie the frontend reads) |
| `commands` | how this project runs `lint`, `typecheck`, `test`, `testRelated`, `e2e`, `build`, `audit` |
| `environments` | `frontendUrl` and `backendUrl` per environment (scripts use the first one, or `--env`) |
| `accounts` | `roles` (name → test e-mail; include **two accounts of the same role** to test foreign data), `passwordEnv` (the variable holding the test password — never in the file; the project `.env` is read too — and `.env.<environment>` first when scripts run with `--env <environment>`), `source` (the seed that creates them) |
| `testEmail` / `testEmailEnv` | the only real inbox e-mails may go to during tests — the address itself, or the name of the variable that holds it (scripts read the shell and the project `.env`, the shell wins) |
| `walkthrough` | `outputDir`, `viewports`, `minTouchTargetPx`, `testDataPrefix`, `notFoundText`, `designSkill`, `domainRules` (your pricing/refund/legal documents), `decisions` (`dbIdsInUrl`, `urlLanguage`, `sentenceCase`), `text.pluralNouns`, `selectors.toast`, extra `sensitiveKeys` / `personKeys`, and `codeRules` (your own mechanical checks) |
| `tables` | `source` (generated DBML) and `base` for the diagrams |

### 2. Constitution

Run `/speckit-constitution` and write the project principles. The bundled `constitution.md` is spec-kit's blank template.

### 3. Table diagrams (Prisma)

```bash
npm i -D prisma-dbml-generator
```

```prisma
// prisma/schema.prisma
generator dbml {
  provider = "prisma-dbml-generator"
  output   = "../dbml"
}
```

`npx prisma generate` now writes `dbml/schema.dbml` — the `tables.source` of the config. Commit it: the table checker compares each feature's planned file with it.

### 4. Quality gates (husky + lint-staged + commitlint)

```bash
npm i -D husky lint-staged @commitlint/cli @commitlint/config-conventional prettier
npm pkg set scripts.prepare=husky
npm run prepare
```

The kit already ships `.husky/pre-commit` (`npx lint-staged`) and `.husky/commit-msg` (`npx --no -- commitlint --edit "$1"`); `npm run prepare` only activates them (`npx husky init` would overwrite the pre-commit hook). `lint-staged.config.mjs` runs on the staged files only:

- `eslint --fix --max-warnings=0` and `prettier --write`;
- **`jest --bail --findRelatedTests --passWithNoTests`**: the tests you created or changed, plus every test that imports a changed file. With Vitest, use `vitest related --run`;
- `prisma format` and `prisma validate` when the schema changes.

A failure blocks the commit. The full suite still runs in CI.

### 5. Architecture rules in ESLint (NestJS + Prisma)

```js
// eslint.config.mjs
import boundaries from './eslint.boundaries.mjs';
export default [...yourConfig, ...boundaries];
```

`eslint.boundaries.mjs` (needs `npm i -D eslint-plugin-import`) enforces what `modulos-backend` teaches:

- only `*.repository.ts` and `adapters/**` import the Prisma client or service;
- a controller never imports a repository (`Controller → Service → Repository`);
- `import/no-cycle`: the module graph stays acyclic (a child never imports its parent; foreign data comes through a port).

Adjust `PRISMA_SERVICE` to your path. Recommended next to it: `@typescript-eslint/no-floating-promises`, `@typescript-eslint/no-explicit-any` and `eqeqeq`.

### 6. The rest

- **`CLAUDE.md`**: adapt it — it tells Claude where project facts live and the quality bar.
- **`.github/`**: issue (story, bug) and PR templates; set a specs link in `ISSUE_TEMPLATE/config.yml` if you want one.
- **Captures**: walkthrough captures can be large. Commit the ones that are evidence, or ignore the automatic ones: `specs/**/captures-*/auto/` in `.gitignore`.

## Use

| Command | What happens |
|---|---|
| `/speckit-specify <description>` | creates `specs/NNN-name/spec.md`; the spec lists its flows (journeys) and, for a refactor, the behaviour that must not change |
| `/speckit-plan` | plan, data model, contracts; then the hooks recommend `/speckit-tables` (`tabelas.planejado.dbml`) and `/speckit-flows` (`fluxos.drawio` + `roteiros/`) |
| edit `fluxos.drawio` / `tabelas.planejado.dbml` | commit the generated files first; then edit freely. The next `/speckit-flows` or `/speckit-tables` (or `/speckit-converge`) reads the diff against git, judges each change and applies only what is valid — intent changes are asked, never assumed |
| `/speckit-tasks` | tasks, plus one walkthrough task per flow script |
| `/speckit-implement` | implementation; the table diagram is regenerated from the real schema |
| `/speckit-converge` | absorbs drawing and diagram edits, then adds the work still missing as tasks |
| walkthrough of a flow | ask Claude to do the walkthrough of `R01` (skill `flow-walkthrough`); it fills `flows.json`, runs the inventory, the scans and the captures, fixes, does the second round and closes with `verify-matrix.mjs` |
| review | ask for a review of the branch or PR (skill `code-analyze`) |

The walkthrough scripts can also run by hand, from the project:

```bash
node .claude/skills/flow-walkthrough/scripts/inventory.mjs --flow R01
node .claude/skills/flow-walkthrough/scripts/scan-code.mjs --flow R01 > specs/001-x/passagem/scan-code-R01.md
SDD_TEST_PASSWORD=... node .claude/skills/flow-walkthrough/scripts/scan-accounts.mjs --flow R01
node .claude/skills/flow-walkthrough/scripts/verify-matrix.mjs specs/001-x/passagem/matrix-R01.md
```

## Working agreements the kit assumes

- **Spec first, then code.** A change of direction is a new spec or an explicit edit by the owner, not a silent drift.
- **Structure comes from the skills, not from the neighbouring module.** Existing code is measured against the skills; it is not the template.
- **Scripts list, people judge.** No script applies a change or approves a matrix cell; the agent reads, judges and asks.
- **History lives in git.** No copies or logs of drawings and diagrams; commit the generated files before editing them.
- **Small, related tests on every commit; the full suite in CI.**
- **Conventional Commits**, and no commit or PR without the owner asking.
- **Tooling in English, documents in the project language.**

## Language status

New content of the kit is in English. `clean-code`, `modulos-backend`, `code-analyze`, the `roteiro-template.md` and the status notes of `tables-dbml.mjs` are still in Brazilian Portuguese (they work as they are); their translation is planned. The walkthrough matrix and reports already follow `project.locale` (`en`, `pt-BR`).

## Upgrading

- **The kit**: `git pull`, then `node install.mjs your-project --force --only .claude/skills,.specify/scripts/node,.specify/templates/overrides,.specify/templates/roteiro-template.md,.specify/sdd.config.schema.json`. Your `sdd.config.json`, `CLAUDE.md`, `extensions.yml` and constitution are not touched.
- **Spec-kit**: upgrade with the Specify CLI (`specify init --here --ai claude --script ps`; see the spec-kit docs). It regenerates the `speckit-*` skills and its own templates; afterwards check that `.specify/extensions.yml` still has the kit hooks. For the bash variant use `--script sh` and change the prerequisites call in `speckit-flows` accordingly (the skill already documents both).

## Developing the kit

```bash
npm test
```
