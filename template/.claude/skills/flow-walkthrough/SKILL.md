# Flow walkthrough — complete, never shallow

A walkthrough ends only when **every screen and every route** of the flow went through **every point**, with evidence, **and** a whole second round found nothing new. Memory is not the list: the list is the **matrix** (`matrix-<flow>.md`), generated from the code, one cell per point. An empty cell blocks the flow; the PR does not go out with an incomplete matrix.

## Language

This skill and its scripts are in English. **What it produces is in `project.locale`** of `sdd.config.json`: the matrix, the scan reports (built-in: `en`, `pt-BR`), the findings, the fixes' messages and the report to the owner.

## Project setup it reads

Every project fact has **one owner**. What the code, the seed or an env file already states is read from there; **`sdd.config.json`** at the repository root holds only what no other file owns (shipped by sdd-flow-kit, filled in per project). No path, account or rule of a project is written in this skill.

| Key | Used for |
|---|---|
| `project.locale` | language of the matrix, reports and findings |
| `frontend.root`, `frontend.pages`, `frontend.router` | screens of a flow (`next-app-router` discovers them; `manual` lists them in `flows.json`) |
| `backend.root`, `backend.framework` | routes of a flow (`nestjs` discovers them; `manual` lists them) |
| read from the code (`nestjs`): prefix, Swagger, health and login routes, login body, session cookie, error body | sign-in, security headers, documentation route, error code and message. Set `backend.*` / `auth.*` only to override |
| read from the env file of the environment: `PORT` (+ prefix) and `FRONTEND_URL` | API and frontend URLs. `.env.test` → `test` (the default), `.env` → `local`, chosen with `--env`; only that file is loaded |
| `accounts.roles`, `accounts.source` | test accounts (never real people) and the seed that creates them; read the password there and pass `--password` (or use `accounts.passwordEnv` / `accounts.password`) |
| `testEmail` / `testEmailEnv` (optional) | the only real inbox e-mails may go to; without it, the addresses of the env file |
| `walkthrough.*` | output folder, viewports, touch target, test-data prefix, not-found text, design skill, domain rules, project decisions, extra checks |

Missing `sdd.config.json`: stop and ask the owner to create it from the template — do not guess paths or accounts.

**Project decisions** (`walkthrough.decisions`) change how a point is judged: `dbIdsInUrl: "ignore"` turns the database-id part of points 14 and 16 into 🚫 with the reason "project decision"; `urlLanguage` is the language of point 16; `sentenceCase: false` drops the capital-letter check of point 7.

**Domain rules** (`walkthrough.domainRules`) are the project's documents (pricing, refunds, legal texts). When the flow touches what one of them covers, read it before points 8 and 15 and check the screen and the server against it. The rule lives in the project, not here.

## Files of a walkthrough

In the walkthrough folder: `<feature>/<walkthrough.outputDir>` when the project uses spec-kit (`.specify/feature.json`), else `<root>/<walkthrough.outputDir>`. The scripts find it by themselves (`--dir` overrides).

```text
<walkthrough dir>/
├── flows.json               # per flow: screens, controllers, route filter, public routes, examples
├── scenarios-<flow>.json    # accounts × calls × screens for the script layer
├── matrix-<flow>.md         # generated by inventory.mjs, filled in during the walkthrough
├── scan-<kind>-<flow>.md    # raw reports of the scans (code, api, security, accounts, screens)
└── captures-<flow>/         # captures, looked at one by one
```

Formats: [`reference/files.md`](reference/files.md).

**With spec-kit** (`speckit-flows`): each flow is a walkthrough script `roteiros/R##-*.md`, born in the plan with everything ⏳. The `R##` of the script is the flow id in `flows.json`. The walkthrough executes the script (happy path, stress, access, visual, absences) and writes back the status, date and evidence of each row; the matrix covers the 18 points. Without spec-kit, the flow is described in `flows.json` and the matrix alone.

## The 18 points

Detail, how to prove and traps of each: [`reference/points.md`](reference/points.md).

| # | Point | Applies to |
|---|---|---|
| 1 | Happy path and stress run for real (screen or real call; "from the code" does not count) | screen, route |
| 2 | Cross-check: every screen and route of the domain listed and walked; route without screen, screen without route, unused route | walkthrough |
| 3 | Second round complete after the fixes, until a round with no new finding | walkthrough |
| 4 | Absences: create, read, edit, delete, cancel, undo, back, leave | screen |
| 5 | Path to the page: reached without typing the URL; shortcuts lead to the right place | screen |
| 6 | Floating notice only when needed; feedback next to the action; error next to the field | screen |
| 7 | Short text, no explaining the mechanism, no security advice; spelling; sentence case; right plural | screen |
| 8 | Locale formats: currency, dates, numbers | screen |
| 9 | States: empty, loading, error with retry, no permission, expired session, network down, double click, two tabs | screen |
| 10 | Clear errors in the project language, from the catalog, never raw; a load failure never becomes an empty list | screen, route |
| 11 | Phone (narrowest viewport): no horizontal scroll, touch targets ≥ `minTouchTargetPx`, nothing covered — **by reviewed capture** | screen |
| 12 | Wide desktop: hierarchy, alignment, nothing repeated — **by reviewed capture** | screen |
| 13 | Accessibility: label bound to the field, name on icon-only buttons, no interactive element inside another, visible focus | screen |
| 14 | Security and data (full list in `reference/points.md`): foreign data blocked (tested with two accounts), attempt limits, `no-store` with a session, redirects only to the own site, protection headers, closed docs in production, dependency audit; database id in the URL per `decisions.dbIdsInUrl` | screen, route |
| 15 | Rule on the server, not only on the screen, with a test; domain rules checked | screen, route |
| 16 | URLs in `decisions.urlLanguage`, clean, no personal data in the bar; database id per `decisions.dbIdsInUrl` | screen |
| 17 | Resolve in the walkthrough (not only record); fix on the spot what is not a full redesign | walkthrough |
| 18 | Before the PR: documents up to date, screens shown to the owner, PR only on the owner's request | walkthrough |

## Protocol (gates in order — do not skip)

Detail and commands: [`reference/protocol.md`](reference/protocol.md).

0. **Setup**: `sdd.config.json` complete for what the flow needs; the flow entry in `flows.json`; frontend and backend up.
1. **Inventory** → `inventory.mjs` creates or updates the matrix. No screen comes from memory.
2. **Code reading** of each screen: every action, state and call. For each route: who calls it, who may, what it returns.
3. **Script** happy path and stress **on the screen**, signed in with the right role.
4. **Absences** screen by screen (point 4) and the path to it (point 5).
5. **Scans**: `scan-code`, `scan-api`, `scan-security`, `screen-probe.js` (wide and narrow), and the script layer `scan-accounts` + `scan-screens`. Every item raised is decided: fixed, or justified in the matrix.
6. **Captures** of every screen at each viewport, saved to disk, **looked at one by one** (points 11 and 12), then the design skill when configured.
7. **Fixes** of everything, with tests, using `commands.*` of the project.
8. **Second round** (steps 3 to 6) over the fixed code.
9. **Closing**: `verify-matrix.mjs` with no failure, documents up to date, report to the owner with the captures of the screens that changed.
10. **PR only on the owner's request.**

## Rules that are not negotiated

- **Privacy, a fixed question on every screen and route:** "should this account see this?" and "could it see or change it?". Whoever is neither the owner nor the team of the resource **does not see the screen**, not even read-only: the API filters in the query (foreign = nonexistent = the same 404) and the page shows the not-found page (`walkthrough.notFoundText`), without form or data. Opening another owner's resource and only failing on save is a defect. Test with two accounts of the same role and with the team (only what the permission covers).
- **Signed out and signed in:** public screens pass as a visitor (header and footer change) and as a signed-in person.
- **Exercise every branch of the screen, do not just look:** each option of a choice, invalid input, submit, empty state, error. Defects live in the branch nobody opened.
- **Every capture is looked at.** When the automation browser stalls, use `capture.mjs` (headless, exact width, no extension). A capture that fails is fixed, not replaced by a measurement.
- **Design of every screen, even with no broken layout:** with the captures at hand, run `walkthrough.designSkill` (when configured) on every screen. "Not broken" is not "good". A finding goes to the matrix (fixed now, unless it is a full redesign — then it is recorded with the owner's decision).
- **Values are never typed by the client:** a total, fee or refund comes from stored data and is computed on the server; the screen shows only what is needed. The domain rules documents say how.
- **Public route with a body:** check its submission limit.
- "From the code", "via the API" instead of the screen, or "measured and passed" instead of the capture **do not count**.
- A stress impossible to simulate stays as a **limitation**, with the reason, and the owner is told. **Only hardware is a limit:** a missing scenario or data (a cancelled item, an account without items, two of something) **is created in the seed of the flow** and exercised.
- Out of scope only by the owner's decision, recorded in the matrix.
- **Scripts add, they never replace** ([`reference/script-layer.md`](reference/script-layer.md)): they give full coverage and raw material, they do not approve a cell, open a screen branch or judge design. Every alert is decided in the matrix. A mechanical defect found by hand becomes a check (the ratchet: `walkthrough.codeRules` or a scenario).
- Test data uses `walkthrough.testDataPrefix` and is cleaned at the end; e-mails go only to `testEmail` (or the address in `testEmailEnv`).
- A laborious flow is the expected case. Do not shorten it to reach the PR.

## Scripts

`<skill>` = this folder: `.claude/skills/flow-walkthrough` in the project (or `~/.claude/skills/flow-walkthrough` when installed for the user). Node 22+, no dependency. Run from the project (any folder below `sdd.config.json`).

| Script | What it does |
|---|---|
| `show-config.mjs [--env <name>]` | what the scripts resolved and where each value came from (config, code, env file, default) |
| `inventory.mjs --flow <id>` | creates or updates `matrix-<id>.md` from the code, keeping what was filled in |
| `verify-matrix.mjs <matrix.md>` | fails while a cell is not done, lacks evidence or justification, or the second round has no date |
| `scan-code.mjs --flow <id>` | static scan of screens and components (points 6–8, 10, 13, 14, 16) + `walkthrough.codeRules` |
| `scan-api.mjs --flow <id>` | public routes: data that should not leave the API |
| `scan-security.mjs --flow <id> [--token]` | attempt limits, unvalidated ids, cache with session, headers, open docs |
| `scan-accounts.mjs --flow <id>` | every call × every account, foreign × nonexistent parity |
| `scan-screens.mjs --flow <id> [--captures <dir>]` | every screen × account × viewport, probe + console + network + page text |
| `capture.mjs <url> <width> <out.png>` | one capture, signed in with `SDD_CAPTURE_TOKEN` |
| `screen-probe.js` / `serve-probe.mjs` | in-page probe for a browser automation tool |

Reports go to a file: `node <skill>/scripts/scan-code.mjs --flow R01 > <dir>/scan-code-R01.md`.
