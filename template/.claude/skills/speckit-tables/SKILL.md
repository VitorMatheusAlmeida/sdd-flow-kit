## User Input

```text
$ARGUMENTS
```

Explicit mode, if given: `create`, `absorb` or `update`. A request in plain text ("remove X", "show the payment tables") is a filter edit. With no argument: `create` if there is no `tabelas.filtro.json`; otherwise `absorb` when `--check` reports hand edits, then `update`.

## Language

This skill and its tooling are in English. **Everything it writes into the feature is in Brazilian Portuguese (pt-BR)**: notes, group titles meant for people, the header and the status notes of `tabelas.dbml` (the script's status notes are pt-BR; other locales are a planned extension). Filter keys and table/column names stay as they are.

Defaults come from `sdd.config.json` at the repository root: `tables.source` (the DBML generated from the schema) and `tables.base` (else `git.baseBranch`). Use them when creating a filter; a filter value always wins.

## What this skill guarantees

```text
specs/<feature>/
├── tabelas.filtro.json      # WHAT the owner wants to see — the owner may edit it by hand
├── tabelas.planejado.dbml   # new or changed tables the plan expects and the schema does not have yet
└── tabelas.dbml             # GENERATED: paste into dbdiagram.io; the owner may edit it there and paste it back
```

`tabelas.dbml` = the filter's tables, read from the current schema (`dbml/schema.dbml`, generated by Prisma) or from the planned file, with the links between them, the enums they use, the groups, and one note per table with the computed status (`NOVA` / `ALTERADA desde <base>: +col, -col, ~col` / `sem mudança` / `PLANEJADA…`) followed by the filter note. Script: `node .specify/scripts/node/tables-dbml.mjs <FEATURE_DIR> [--check | --force]`.

**Hand edits are protected, not applied.** The script writes a signature in the first line. When the owner edits the file in dbdiagram and pastes it back, the content no longer matches the signature: `--check` reports it and a normal run **refuses to write**. The script never applies the edit — understanding it, judging it and moving what is valid into the planned file or the filter is your job (mode absorb). Only then run with `--force`. History lives in git: the base for "what changed" is the last commit.

### `tabelas.filtro.json`

```json
{
  "title": "Spec 003 — Inscrição em cursos",
  "project": "my_product_003",
  "source": "dbml/schema.dbml",
  "base": "main",
  "baseLabel": "a main antes da spec 003",
  "planned": "tabelas.planejado.dbml",
  "groups": { "inscricao": ["Course", "Enrollment"] },
  "notes": { "Enrollment": "003: nasce na inscrição", "Course.seatLimit": "003: limite de vagas" }
}
```

- `groups` is the filter: only tables listed in a group appear. They become `TableGroup` in dbdiagram.
- `notes`: key `Table` (table note) or `Table.column` (column note), in pt-BR. A note says what the feature changes there.
- `base`: the branch or commit against which "touched" is measured (default: `tables.base` or `git.baseBranch` of `sdd.config.json`). A feature that continues another one already merged may use the commit before the merge, with a readable `baseLabel`.
- Filters written before the English tooling used Portuguese keys (`grupos`, `notas`, `planejado`…); the script still reads them.

### `tabelas.planejado.dbml`

DBML written from the plan's `data-model.md`, with only what **does not exist yet** in the schema:

- new table: complete;
- changed table: a **full copy of the current one** (from `dbml/schema.dbml`, without relation fields) with the change applied — new column added, removed column taken out. The script shows the difference in the note;
- new or changed enum: complete;
- new link: `Ref:` or `ref:` on the column.

When implementation catches up with the plan, the script warns "already matches the schema": take the table out of the planned file.

## Step 1 — Context

Run `.specify/scripts/powershell/check-prerequisites.ps1 -Json -PathsOnly` and take `FEATURE_DIR`. If `prisma/schema.prisma` is newer than `dbml/schema.dbml`, run `npx prisma generate` first (it regenerates the DBML; it does not touch the database).

## Mode create

1. Read `spec.md`, `plan.md` and `data-model.md`.
2. **Pick the tables**, in three layers:
   - the ones the plan creates or changes (from `data-model.md`);
   - the ones the branch already touched: run the script once with a minimal filter and read the "touched … outside the filter" warning;
   - the ones that point to those (foreign key in `dbml/schema.dbml`), when the feature changes what the link means. A neighbor that only exists for existing's sake stays out — the diagram is for seeing, not for listing.
3. Group by business subject, not by code module. Write, in pt-BR, the notes on what the feature changes in each table.
4. Write `tabelas.planejado.dbml` with what the plan expects and the schema lacks.
5. Generate, and show the owner the list of groups and tables, asking whether to remove or add any.

## Mode absorb — the owner edited tabelas.dbml

1. **Read what changed:** `git diff -- <FEATURE_DIR>/tabelas.dbml` (base: the last commit). The diff is raw material, not a verdict.
2. **Understand each change** in schema terms: new table, new or removed column, changed type or nullability, new or removed link, new enum value, moved table, edited note.
3. **Judge whether each change is valid.** Check, for each one:
   - **The schema conventions** (`modulos-backend`, `modelagem-prisma.md`): `@@map` in plural `snake_case`, `Timestamptz` instants, `createdAt`/`updatedAt`, junction with composite key, `onDelete` by meaning, natural key with `@unique`.
   - **Table ownership** (`propriedade-de-tabelas.md`): the new table or column has one owner module; a link across domains is a foreign key, not a reason to navigate.
   - **The spec and the flows:** the change serves a story, an FR or an input in `fluxos.drawio` — or it is a change of intent, which only the owner decides. A new column with no input, route or rule behind it is a question.
   - **Compatibility:** a removed or renamed column that the code or production data uses; a new required column without default on a table with data.
   - **What is only visual** (moving a table, a group, a note): goes to the filter, not to the planned file.
4. **Report the evaluation** in pt-BR, one line per change: change · valid? · why · where it goes (planned file, filter, `data-model.md`, spec).
5. **Apply what is valid and derived**: the planned file (`tabelas.planejado.dbml`) and the filter. **Ask before** anything not valid as written (propose the fix) and before changing `data-model.md`, spec or contracts.
6. Run `node .specify/scripts/node/tables-dbml.mjs <FEATURE_DIR> --force` and confirm the regenerated file shows the absorbed changes (status `PLANEJADA, muda a atual: …`). Suggest the commit that closes the change; do not commit without the owner's permission.

## Mode update

1. Generate again. Read the warnings and handle each one:
   - "touched … outside the filter": **ask** whether they go in (the filter is the owner's choice; never add on your own);
   - "already matches the schema": take the table out of the planned file;
   - "in the planned file but outside the filter groups": ask which group it goes into, or whether it leaves the planned file;
   - unknown table or a `ref` to a table outside the filter: fix the filter or the planned file.
2. If the plan changed (`data-model.md` newer than the planned file), update the planned file.
3. Short report in pt-BR: new, changed and planned tables that changed since the last generation, and the questions.

## Owner request ("remove X", "add Y", "group it like this")

Edit only `tabelas.filtro.json` (or the planned file, if it is a new design), generate, and confirm what changed.

## Rules

- `tabelas.dbml` is generated; hand edits are absorbed through mode absorb, never overwritten and never applied by the script.
- The filter is the owner's choice: the skill suggests, the owner decides what goes in.
- No history files: git is the history.
- No commits without the owner's permission. No migration, seed or database access.
- Do not edit the `SKILL.md` files generated by spec-kit (`speckit-*` other than this one and `speckit-flows`).
