## User Input

```text
$ARGUMENTS
```

Explicit mode, if given: `create`, `absorb` or `update`. With no argument: `create` if there is no `tabelas.planejado.dbml`; otherwise `absorb` when `git status` shows it modified by hand, then `update`. A request in plain text ("remove X", "add Y") is an edit of the file.

## Language

This skill and its tooling are in English. **Everything it writes into the feature is in `project.locale` of `sdd.config.json`** (default pt-BR): comments, notes, group names meant for people. Table, column and enum names stay as they are in the schema.

## What this skill guarantees

```text
specs/<feature>/
└── tabelas.planejado.dbml   # the only output: paste it whole into dbdiagram.io
```

The file holds **only the tables of this spec**:

- the tables the spec creates, complete;
- the tables the spec changes, as a **full copy of the current one** (from `dbml/schema.dbml`, without the Prisma relation fields) with the change applied;
- the tables they reference (`ref:` targets), copied from the schema even when the spec does not change them, so every link resolves;
- every enum the tables use: new or changed ones as planned, the others copied from the schema.

A table that only matters because a rule of the spec talks about it, without a column or link changing, stays out: the rule lives in the spec.

Each table carries a `Note` in the locale that starts with its status (`Nova.`, `Muda: <what>.`, `Sem mudança no schema.` for a referenced table) followed by what the spec changes there. Tables go into `TableGroup`s by business subject (each table in one group). The file starts with a `Project` block and a comment that names the spec.

Checker: `node .specify/scripts/node/tables-dbml.mjs <FEATURE_DIR>`. It never writes. It exits 1 when the file would not open on its own (a ref to a table or column the file lacks, a group member that is not a table, a duplicate, an enum of the schema used without being defined). It lists, per table, how it differs from the current schema, which is how you see what is new, what changes and what was already implemented.

History lives in git: the base for "what changed" is the last commit of the file.

## Step 1 — Context

Run `.specify/scripts/powershell/check-prerequisites.ps1 -Json -PathsOnly` and take `FEATURE_DIR`. Read `sdd.config.json` for `project.locale` and `tables.source`. If `prisma/schema.prisma` is newer than the DBML source, run `npx prisma generate` first (it regenerates the DBML; it does not touch the database).

## Mode create

1. Read `spec.md`, `plan.md` and `data-model.md`.
2. Pick the tables: the ones `data-model.md` creates or changes; then the ones they reference. Nothing else.
3. Write `tabelas.planejado.dbml` as described above.
4. Run the checker until it passes, and compare its status list with `data-model.md`: a table listed as "same columns as the schema" that the plan changes means the change is missing from the file.
5. Show the owner the groups and tables.

## Mode absorb — the owner edited the file in dbdiagram and pasted it back

1. Read what changed: `git diff -- <FEATURE_DIR>/tabelas.planejado.dbml`. The diff is raw material, not a verdict.
2. Understand each change in schema terms: new table, new or removed column, changed type or nullability, new or removed link, new enum value, moved table or group, edited note.
3. Judge whether each change is valid:
   - **The schema conventions** (`modulos-backend`, `modelagem-prisma.md`): `@@map` in plural `snake_case`, `Timestamptz` instants, `createdAt`/`updatedAt`, junction with composite key, `onDelete` by meaning, natural key with `@unique`.
   - **Table ownership** (`propriedade-de-tabelas.md`): the new table or column has one owner module.
   - **The spec and the flows:** the change serves a story, an FR or an input in `fluxos.drawio`, or it is a change of intent, which only the owner decides. A new column with no input, route or rule behind it is a question.
   - **Compatibility:** a removed or renamed column that the code or production data uses; a new required column without default on a table with data.
4. Report the evaluation in the locale, one line per change: change · valid? · why · what else it touches (`data-model.md`, spec, contracts).
5. Keep what is valid in the file; propose the fix for what is not. **Ask before** changing `data-model.md`, the spec or the contracts.
6. Run the checker. Suggest the commit; do not commit without the owner's permission.

## Mode update — the plan or the schema moved

1. If `data-model.md` changed since the file's last commit, bring the change into the file.
2. Run the checker. "same columns as the schema" on a table the spec changes means it was implemented: keep it in the file (it is the picture of the spec), and say so.
3. Short report: tables that changed since the last commit, and the questions.

## Rules

- The file is the only output: no generated copy, no filter file.
- Only the tables of the spec and what they reference. The owner decides what goes in; ask before adding a table the plan does not name.
- No commits without the owner's permission. No migration, seed or database access.
- Do not edit the `SKILL.md` files generated by spec-kit (`speckit-*` other than this one and `speckit-flows`).
